这个是一个自研的量化因子挖掘项目；项目的历程是这样子的：它经历过多轮迭代和反复。该项目原先是 AlphaSage 这篇论文的 GitHub 实现，是一种结合了 GFlowNet 神经网络以及复杂的因子挖掘、迭代奖励激励函数等机制的一套框架体系。

&#x20;

但是，它之前目前仅支持硬编码适配于股票的基础量价信息。warning我在这个项目上做输入输出和工程端的优化，简单来说：

1. 前端适配\
   让它适配于更完善的因子数据，包括但不限于：\
   (a) 股票的量价、基本面、财务数据\
   (b) 特色的筹码、订单数据\
   (c) 适配于期货、期权、外汇、宏观指数、国内国外指数等各种数据
2. 后端输出端\
   形成更完善的一套因子挖掘体系。不仅是从 AlphaSage（或叫 AlphaGFN）这样一个研究范式的项目，转为一个能够实现工程化、高通量批量挖掘的体系。
3. 自动化挖掘\
   能够按照不同的域、不同的参数、不同的类别和挖掘条件，来批量高效率地进行挖掘。

这是项目的核心。因此，在修改过程中，它经过了几轮迭代：

1. 初始阶段与第一轮改造\
   原来 AlphaSage GitHub 项目中的运行接口是 train\_gfn，使用的是 Qlib 的数据。（alphagen\_generic、alpha\_gfn）后来我弃用了 Qlib 数据（alphagen\_qlib），但是一些模块接口没有迁移，做了第一轮改造，使用了一些完善的个人tushare（Parquet 数据），即 Parquet Loader。
2. 版本升级与改进\
   随后改进出了 train\_gfn\_v2（src\train\_gfn\_v2.py）和 Parquet Loader v2（src\alphagen\_generic\parquet\_feature\_loader\_v2.py、src\alphagen\_generic\feature\_registry\_manager\_v2.py），主要解决以下问题：\
   (a) 源代码的 GFN 库版本较低，升级后许多第三方库的导入方式发生了变化\
   (b) 数据端完全改成了自研的 duckDB 数据库（src\datahub\duckdb\_hub.py）
3. 数据库与工程文档\
   duckDB 的数据位置在另一个项目的根目录下（不在本项目根目录下）。具体的工程文档可以参考 TuShare-data-Readme 文件。目前 duckdb 的导入已经通过测试（test\_duckdb\_integration.py文件），实现了正确导入，因此最开始的接入数据已经没问题了。但（test\_duckdb\_integration.py仍然存在问题）
4. 因子配置的探索\
   在接入数据后，关于如何进行因子配置，中间经历了几轮反复，主要分为两波：\
   (a) 第一波：使用 Kimi 2.5 生成。这部分代码包含了中文注释，代码量较大，但特征属于冗余内容较多，框架结构不够清晰。（src\datahub、src\data\_prep、src\integration、src\progress）\
   (b) 第二波：由 Gemini 1.5 Flash 实现。它做了一些调整，但也不够充分。

目前存在的问题是，我每次实现都会有一定的工程文档，但并没有一个从头到尾接续的完整文档。从开始到现在大概出现了六七个工程文档，每个都是按照当前阶段的任务来实现的，所以总体的协调性和工程性并不强。

目前的情况，我希望首先能有效跑通，这是一个核心问题。目前数据导入已经可以了，但在因子配置方面存在一些导入调用不清晰、模块冗余以及结构衔接不完善的问题，这些都影响了导入。同时，由于 GFN 库之前的升级，一些模块可能会造成问题，接口也没有统一。

针对后续的优化，我有以下几点要求：

1. 遵循核心研究范式\
   你要谨慎对待一个问题：我要求的挖掘研究范式必须完全遵循 Alpha Sage（即原来 train-gfn 库）的那套体系。我后来在自己挖掘的过程中做了一些尝试，比如 AST 算法生成树文件或者 Simple Neural Network，但注意这些可能是当时并不完善的工程文档引入的。我最后核心调用的并不是自己构建的那套挖掘体系，我做的其实只是前端数据输入、因子配置和后端挖掘流程的工程化保存。核心的挖掘框架引擎（Engine）是调用原有的，因此代码中可能存在一些错误的冗余，导致你错误地关注了非核心部分。这非常重要，需要解决它。
2. 完善工程结构并去冗余\
   我希望项目整体的工程结构更加完善。现在你会发现像 Parquet Loader 或者 DuckDB 都可以导数据，我做了一些迁移，但迁移后显得有些冗余。有些文件虽然有一定功能，但要么没有被调用，要么存在多条路径但主路径未启用。这其实是因为我先后多次进行工程文档设计，导致了重复建设和“重复造轮子”的问题，同时也缺乏一个完善的工程方向体系。
3. 配置逻辑的专业设计\
   我认为整个项目已经进入了 80% 的进度，最后跑通会比较快，但仍存在一些问题。比如目前有 YAML 和 JSON 文件的配置（config\datasets\cn\_stock\_daily\_v1.yaml较为新，enhanced\_tushare\_daily\_A.json是之前kimi生成的），你需要思考并读取一下，看看到底哪种配置方式更好。是数据端导入用一种配置、后来挖掘用另一套配置，还是有更统一的设计？这个逻辑应该设计得更加专业和完善。一些要求要保留合并实现；

我希望整个项目体系能以顶级工程化的视角来看。我开始的野心比较大，并不喜欢一步步零敲碎打地更新，那样很痛苦，我希望从一开始就建立一个全面的机制。

以上我讲的都是最核心的点。你可以参考中间的工程文档，具体包括读取 GitHub 上的项目来了解当前最新的进度情况。
