# 一、总体判断：当前项目应当“收束”，不是继续扩张

`src/` 当前同时存在 `alpha_gfn`、`alphagen`、`alphagen_generic`、`alphagen_qlib`、`datahub`、`integration`、`mining`、`progress`、`expression`、`gan`、`evaluation` 等目录，另外还有 `train_gfn.py`、`train_gfn_v2.py`、`train_gfn_v2_enhanced.py`、`preprocess_features.py`、`preprocess_features_v2.py`、`build_digged_factors.py`、`run_adaptive_combination.py` 等入口或半入口脚本。这个结构的最大风险是：**每个模块看起来都有功能，但没有唯一执行主干**。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-third-425/src "Finance_factor_digging/src at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))

因此，我建议把项目最终压成下面这条主链：

```
config/jobs/*.yaml
    -> mining.job_spec.MiningJobSpec
    -> alphagen_generic.dataset_meta.DatasetMeta
    -> alphagen_generic.feature_registry_manager_v2.FeatureRegistryManagerV2
    -> datahub.duckdb_hub.DuckDBDataHub
    -> alphagen_generic.parquet_feature_loader_v2.ParquetFeatureLoaderV2
    -> mining.family_search_space.build_family_search_space

    -> alpha_gfn.modules.SequenceEncoder
    -> alpha_gfn.alpha_pool_v2.AlphaPoolGFN
    -> alpha_gfn.gflownet.EntropyTBGFlowNet
    -> mining.factor_registry / progress store / screen_factors

```

这条链的原则是：

```
alphagen/
    原始 AlphaSage / AlphaGen 表达式、算子、tree、AlphaPool 基础能力。
    不塞数据源、不塞 YAML、不塞 DuckDB、不塞期货/外汇/宏观特判。

alpha_gfn/
    GFN 搜索、环境、policy、encoder、GFN loss、AlphaPoolGFN。
    不负责读数据、不负责解析数据项目、不负责构造资产字段。

alphagen_generic/
    本项目的“通用数据契约层”。
    负责 DatasetMeta、FeatureRegistry、LoaderV2、FactorFamilyConfig、RunArtifacts。

datahub/
    DuckDB / Arrow / 元数据 / 健康检查层。
    只负责从数据项目读表、校验字段、分块返回数据。

mining/
    唯一工作流层。
    负责 job spec -> dataset -> loader -> search space -> GFN -> pool -> output。

data_prep/
    原子字段物化层。
    负责 raw / filled / atomic 的构建，但不参与 GFN 搜索逻辑。

evaluation/
    因子评估、筛选、ICIR、TopK、稳定性、相关性去重。

```

最关键的一句话：**你要做的是把“新数据、新配置、新输出”接到 AlphaSage / AlphaGFN 主线，而不是再造一个新的因子挖掘引擎。**

## P0-3：`src/expression/ast.py` 必须退出主链

当前分支存在 `src/expression/ast.py`，文件头部标注为 “Expression AST nodes for factor mining”。它定义了另一套 `ExprNodeType`、`ExprNode`，并且 `hash()` 里使用了 `hashlib.blake3`。标准库 `hashlib` 没有 `blake3`，除非额外安装第三方 `blake3` 包，否则这里本身就是潜在运行错误。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-third-425/src/expression/ast.py "Finance_factor_digging/src/expression/ast.py at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))

```
alphagen.data.expression.Expression
alphagen.data.tree.ExpressionBuilder
src.expression.ast.ExprNode

```

这会直接破坏：

```
表达式生成
表达式求值
表达式序列化
表达式 hash
表达式缓存 key
因子回放
因子注册表

```

结论：

```
src/expression/ast.py
    不允许被 mining、alpha_gfn、alphagen_generic、evaluation 主链 import。

处理方式：
    1. 移动到 src/experimental/expression_ast.py；
    2. 或保留文件但加警告，并删除主链 import；
    3. 若确需表达式 JSON，写 alphagen Expression <-> canonical JSON 的转换器，而不是第二套 AST。

```

# 五、数据层：DuckDB 是默认主通道，Parquet 只是兼容通道

## 5.1 当前 LoaderV2 的问题

`ParquetFeatureLoaderV2` 现在支持 raw / filled / atomic 三层，也有 `read_mode=raw|filled|atomic|prefer_filled|stack|mixed`。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-third-425/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))

但问题是：

1. `_resolve_input_files()` 同时处理 DatasetMeta、DuckDB 表名、本地文件路径，职责太杂。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-third-425/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))
2. `_build_mixed_view()` 的优先级是 `filled > raw > atomic`，这不合理；atomic 不是 raw 的 fallback，而是可选的“派生特征层”。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-third-425/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))
3. `_load_parquet_data()` 既判断 DuckDB 表，又判断本地路径，还尝试自动补 `.parquet` 后缀，最后仍倾向将数据读成 DataFrame，再转 tensor。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-third-425/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))
4. 对大规模 DuckDB 数据来说，默认 `.to_pandas()` 会破坏列裁剪、分块和 Arrow 流式优势。

## 5.2 LoaderV2 应改成“数据视图构造器”

建议保留 `ParquetFeatureLoaderV2` 名称，避免大改 import，但内部拆成：

```
@dataclass(frozen=True)
class LayerSource:
    layer: Literal["raw", "filled", "atomic"]
    source_type: Literal["duckdb_table", "parquet_file"]
    name: str
    date_col: str
    code_col: str
    available_columns: set[str]


@dataclass(frozen=True)

核心函数改为：

def _resolve_feature_plan(self) -> list[tuple[str, str, str]]:

    """
    只通过 DuckDBDataHub.scan() 读必要列。
    """

def _load_parquet_batches(self, plan) -> Iterator[pa.RecordBatch]:
    """
    兼容 parquet 文件。
    """

def _assemble_tensor_from_batches(self, batches) -> tuple[torch.Tensor, pd.Index, pd.Index]:
    """
    临时可以用 pandas pivot；
    后续再改 Arrow -> NumPy/Torch 分块。
    """

```

`read_mode` 改成：

```
raw:
    只读 raw feature。

filled:
    只读 filled feature。

atomic:
    只读 atomic feature。

stack:
    raw + atomic 显式拼接。
    这是 GFN 默认模式。

mixed:
    删除或改名 legacy_mixed。

```

不要再让 `mixed` 以 `filled > raw > atomic` 做 fallback。正确思想是：

```

```

# 八、GFN 主线：不要改变 AlphaSage 范式，只修接口

你的核心要求是“必须遵循 AlphaSage / AlphaGFN 研究范式”。落实到代码上，就是：

GFN 主线应是：

```

    负责 action mask、token 序列、表达式构造、终止状态、reward 调用。

SequenceEncoder
    负责编码状态。

DiscretePolicyEstimator
    负责 forward/backward policy。

EntropyTBGFlowNet
    负责 TB loss + entropy bonus。

AlphaPoolGFN
    负责表达式评估、IC、互相关、多样性、新颖性、入池策略。

```

`mine_factors.py` 当前已经在搭这条链，包括 `AlphaPoolGFN`、`GFNEnvCore`、`SequenceEncoder`、`EntropyTBGFlowNet` 和 sampler。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-third-425/src/mining/mine_factors.py "Finance_factor_digging/src/mining/mine_factors.py at feature/non-data-progress-third-425 · 789453/Finance_factor_digging · GitHub"))

```
# src/alpha_gfn/torchgfn_compat.py

class TorchGFNCompatSampler:
    def __init__(self, sampler):
        self.sampler = sampler

    def sample_trajectories(self, env, n: int, save_estimator_outputs: bool = False):
        if hasattr(self.sampler, "sample_trajectories"):
            return self.sampler.sample_trajectories(
                env=env,
                n=n,
                save_estimator_outputs=save_estimator_outputs,
            )

        if hasattr(self.sampler, "sample"):
            return self.sampler.sample(n_trajectories=n)

        raise RuntimeError("Unsupported torchgfn sampler API")

```

训练循环只写：

```
trajectories = compat_sampler.sample_trajectories(
    env=context.env,
    n=batch_size,
    save_estimator_outputs=context.job_spec.entropy_coef > 0,
)

loss = context.gfn.loss(env=context.env, trajectories=trajectories)

```

这样 GFN 库版本升级的影响只在一个文件里处理。

# 十五、最终结论

当前项目最值得保留的不是 `train_gfn_v2_enhanced.py` 这类“大杂烩增强入口”，而是已经成型的这组核心件：

```
mining.mine_factors
MiningJobSpec
DatasetMeta
FeatureRegistryManagerV2
ParquetFeatureLoaderV2
DuckDBDataHub
alphagen.data.expression
alpha_gfn.alpha_pool_v2
alpha_gfn.modules
alpha_gfn.gflownet

```

真正要删减或降级的是：

```
src/expression/ast.py
src/train_gfn_v2_enhanced.py
integration/pipeline.py 的主入口地位
gan/*
重复 loader / registry / preprocess 入口
旧 JSON 大配置作为 source of truth 的地位

```

最优先的修改顺序是：

```
1. 补齐 alpha_gfn.env.core.GFNEnvCore；
2. 固定 train_gfn_v2.py -> mining.mine_factors 这条唯一入口；
3. 归档 train_gfn_v2_enhanced.py；
4. 把 src/expression/ast.py 移出主链；
5. 用 YAML 固化 DatasetMeta / FactorFamily / JobSpec；
6. LoaderV2 改成 DataView 构造器；
7. DuckDBDataHub.scan 成为默认读取路径；
8. FeatureRegistryManagerV2 变成字段权限系统；
9. 原子层只做小而稳的 canonical fields；
10. 候选因子输出、筛选、生命周期管理独立成后处理链。

```

这套改法的核心不是推翻你现在的项目，而是把它从“多轮文档驱动产生的半成品集合”压缩成一条明确主线：**AlphaSage / AlphaGFN 负责挖掘范式，DatasetMeta / Registry / DataHub / Loader 负责输入工程化，Mining / Evaluation / Registry 负责作业和输出工程化。**
