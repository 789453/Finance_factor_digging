下面这份是基于我刚读到的 `feature/non-data-progress-second` 分支代码结构给出的**修改指导**，重点是“如何改当前代码、如何收束架构、如何减少破坏、如何接好 alphasage/alpha\_gfn/alphagen/alphagen\_generic/alphagen\_qlib”，而不是建议你新写一套系统。我的判断是：这个项目最后 10% 卡住的核心不是功能少，而是**已有模块的边界、入口、配置、数据契约和 GFN 调用链没有被统一成一条清晰主线**。

# 一、总判断：当前项目应该“收束”，不是“重构扩张”

当前分支已经不是一个空项目。顶层目录已有 `config/`、`data/`、`prompts/`、`src/`、`test_registry/`，并且 README 已经把目标系统描述为“数据分层、因子族 YAML、挖掘作业 job spec、DatasetMeta、ParquetFeatureLoaderV2”的框架。也就是说，项目方向已经写出来了：raw / filled / atomic 多层数据、YAML 因子族、job spec 驱动挖掘、用 `DatasetMeta` 和 `ParquetFeatureLoaderV2` 管理数据读取。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second "GitHub - 789453/Finance_factor_digging at feature/non-data-progress-second · GitHub"))

`src/` 当前包含 `alpha_gfn`、`alphagen`、`alphagen_generic`、`alphagen_qlib`、`data_prep`、`mining` 等模块，同时还有 `train_gfn.py`、`train_gfn_v2.py`、`build_digged_factors.py`、`preprocess_features.py`、`preprocess_features_v2.py` 等入口脚本。问题不是入口不够，而是入口太多，且有些入口还是半集成态。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src "Finance_factor_digging/src at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

当前最应该避免的方向是：继续新增“适配器”“新 AST”“新 search adapter”“新 unified runner”“新表达式体系”。这些会把项目最后 10% 的复杂度继续推高。正确方向是：**把已有的** **`mining`** **作为工作流层，把** **`alphagen_generic`** **作为数据/元数据/注册表层，把** **`alpha_gfn`** **作为 GFN 搜索层，把** **`alphagen`** **作为表达式和 AlphaPool 的基础层，把** **`alphagen_qlib`** **作为数据计算/回测兼容层**。也就是说，不要另起炉灶，而是把已有层级压实。

我建议你把项目的最终架构压成这条主调用链：

```
config/jobs/*.yaml
    -> mining.job_spec.MiningJobSpec
    -> mining.mine_factors.build_mining_context(...)
        -> alphagen_generic.dataset_meta.DatasetMeta
        -> alphagen_generic.feature_registry_manager_v2.FeatureRegistryManagerV2
        -> alphagen_generic.parquet_feature_loader_v2.ParquetFeatureLoaderV2
        -> mining.family_search_space.build_family_search_space(...)
            或 alpha_gfn.search_space_v2.build_search_space(...)
        -> alphagen.data.expression.Feature / Ref / operators
        -> alpha_gfn.env.core.GFNEnvCore
        -> alpha_gfn.modules.SequenceEncoder
        -> alpha_gfn.alpha_pool_v2.AlphaPoolGFN
        -> alpha_gfn.gflownet.EntropyTBGFlowNet
        -> torchgfn.sampler / policy / loss

```

这条链的重点是：**job spec 是唯一任务入口，DatasetMeta 是唯一数据契约，FeatureRegistryManagerV2 是唯一字段注册表，ParquetFeatureLoaderV2 是唯一默认读取器，alphagen 的 expression 是唯一表达式 AST，alpha\_gfn 是唯一 GFN 搜索实现。**

# 二、当前代码的真实结构和主要矛盾

## 2.1 当前模块分工已经存在，但没有被强制执行

当前 `src/alpha_gfn` 包含 `alpha_pool.py`、`alpha_pool_v2.py`、`cache_manager.py`、`config.py`、`gflownet.py`、`modules.py`、`preprocessors.py`、`search_space.py`、`search_space_v2.py`。这说明 GFN 相关能力已经在 `alpha_gfn` 下形成独立层。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src/alpha_gfn "Finance_factor_digging/src/alpha_gfn at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`src/alphagen` 包含 `data`、`models`、`rl`、`trade`、`utils` 等目录，应该被看成 alphasage / alphagen 原有核心，包括表达式、AlphaPool、RL 环境、模型等，不应该在这里做大面积项目业务改造。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src/alphagen "Finance_factor_digging/src/alphagen at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`src/alphagen_generic` 包含 `dataset_meta.py`、`factor_family_config.py`、`feature_registry.py`、`feature_registry_manager.py`、`feature_registry_manager_v2.py`、`parquet_feature_loader.py`、`parquet_feature_loader_v2.py`、`sample_pool_builder.py`、`task_config.py`、`run_artifacts.py` 等文件。这个包本质上就是你们项目自己的“通用数据与配置适配层”，最应该承接“期货、期权、指数、外汇、宏观、多频率、多字段、YAML 配置”的工作。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src/alphagen_generic "Finance_factor_digging/src/alphagen_generic at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`src/mining` 里已有 `factor_registry.py`、`family_search_space.py`、`job_spec.py`、`mine_factors.py`、`screen_factors.py`。这说明“任务编排层”已经存在，不需要另写一个新的大 orchestration 模块。应当把它修成真正主入口。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src/mining "Finance_factor_digging/src/mining at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

所以我对当前项目的第一条修改原则是：

> **不要新建新的架构层。只允许把已有层的职责收紧。**

模块职责应该固定为：

```
alphagen/
    原 alphasage/alphagen 核心表达式、token、tree、AlphaPool、RL 组件。
    原则：不做业务扩展，不塞数据源逻辑，不塞 YAML，不塞期货/外汇专用判断。

alpha_gfn/
    GFN 搜索实现、搜索空间、pool 扩展、torchgfn 对接。
    原则：只接受已经准备好的 feature_enum、operators、delta_times、constants、target、stock_data。
    不关心数据从 CSV、Parquet、Qlib、期货、宏观还是外汇来。

alphagen_generic/
    本项目的数据契约层。
    负责 DatasetMeta、FeatureRegistry、ParquetFeatureLoaderV2、factor_family_config、task_config。
    这里应该接住所有跨资产、多字段、多层数据和 YAML 配置。

data_prep/
    数据预处理层。
    负责 raw / filled / atomic parquet 产物，不直接参与 GFN 搜索。

mining/
    工作流层。
    负责从 job_spec 加载任务，组装 DatasetMeta、FeatureRegistry、Loader、SearchSpace、GFN、Pool、日志、输出。

```

当前“最后 10% 很难配上”的根因是：这些职责在代码里写出来了一半，但实际调用链没有统一。`train_gfn.py`、`train_gfn_v2.py`、`mining/mine_factors.py` 都在做一部分组装；`ParquetFeatureLoader` 和 `ParquetFeatureLoaderV2` 并存；`FeatureRegistryManager` 和 `FeatureRegistryManagerV2` 并存；`search_space.py`、`search_space_v2.py`、`mining/family_search_space.py` 都能构造搜索空间；这会让每个 bug 都变成“到底是哪条入口在生效”的问题。

# 三、最核心的整改目标：一条主入口，多个兼容入口

## 3.1 主入口必须是 `mining.mine_factors`

`mining/job_spec.py` 已经有 `MiningJobSpec`，必填字段包括 `job_id`、`name`、`dataset_id`、`family_id`、`segment_name`、`train_start`、`train_end`、`test_start`、`test_end`；可选字段包括 `n_episodes`、`pool_capacity`、`encoder_type`、`entropy_coef`、`label_days`、`max_expr_length`、`status_filter`、`max_backtrack_days`、`max_future_days`、`use_filled`、`cache_root`、`output_dir`、`seed`、`cuda` 等。这个定义已经足够作为主任务接口。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/job_spec.py "Finance_factor_digging/src/mining/job_spec.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`mining/mine_factors.py` 已经有 `MiningContext`，它在初始化中构建数据加载器、目标表达式和搜索空间；也已有 `build_mining_context(...)` 和 `mine_factors(...)`。当前问题是：`mine_factors(...)` 只是初始化 `AlphaPoolGFN` 后返回 `'status': 'initialized'`，注释里写“这里可以集成 GFN 训练逻辑”，所以它还不是完整执行入口。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/mine_factors.py "Finance_factor_digging/src/mining/mine_factors.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

这就是当前架构最关键的断点：**项目已经有“官方工作流入口”的壳，但实际训练逻辑仍然在** **`train_gfn.py`** **/** **`train_gfn_v2.py`** **里游离。**

修改指导：

1. **不要再新建** **`run_factor_mining.py`、`AlphaGFNSearchAdapter`、`UnifiedAlphaRunner`。**
2. 把 `mining.mine_factors.mine_factors(...)` 改成真正的主入口。
3. `train_gfn.py` 只保留为 legacy CLI。
4. `train_gfn_v2.py` 只保留为 debug / compatibility CLI。
5. 真正的生产调用统一为：

```
PYTHONPATH=src python -m mining.mine_factors \
  --job_spec config/jobs/cn_futures_daily_pv_ts.yaml \
  --dataset_meta config/datasets/cn_futures_daily_v1.yaml

```

或者如果暂时不加 CLI 参数解析，也至少让代码级入口统一为：

```
from mining.mine_factors import mine_factors

result = mine_factors(
    job_spec_path="config/jobs/cn_futures_daily_pv_ts.yaml",
    dataset_meta_path="config/datasets/cn_futures_daily_v1.yaml",
)

```

`train_gfn.py` 目前会直接导入 `alphagen.rl.env.wrapper.action2token`、`alphagen.data.expression.*`、`alphagen_generic.features.*`、`ParquetFeatureLoader`、`FeatureRegistryManager`、`DatasetMeta`、`alpha_gfn.config`、`GFNEnvCore`、`SequenceEncoder`、`AlphaPoolGFN`、`EntropyTBGFlowNet`、`build_search_space`、`CacheManager`、`torchgfn` 等，然后自己构造 loader、feature enum、target、pool、env、sampler、保存 args。这条逻辑已经太重，不适合继续作为主入口。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/refs/heads/feature/non-data-progress-second/src/train_gfn.py "raw.githubusercontent.com"))

`train_gfn_v2.py` 的描述是支持 job spec 和因子族配置，同时保持向后兼容；但它仍然有 v1/v2 loader、v1/v2 registry、alpha\_pool\_v2 等混合导入。它可以作为过渡入口，但不能继续让它和 `mining.mine_factors` 平行发展。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/refs/heads/feature/non-data-progress-second/src/train_gfn_v2.py "raw.githubusercontent.com"))

建议改法：

```
P0 修改：
- mining.mine_factors.mine_factors(...) 变成唯一完整流程。
- train_gfn.py 改成 legacy wrapper，只调用旧逻辑或提示使用 mining.mine_factors。
- train_gfn_v2.py 改成 thin wrapper，只解析 CLI，然后调用 mining.mine_factors.mine_factors(...)。

```

示意代码，不是要求新建文件，而是改 `src/train_gfn_v2.py` 末尾的 CLI 逻辑：

```
# src/train_gfn_v2.py

def main():
    args = parse_args()

    from mining.mine_factors import mine_factors

    result = mine_factors(
        job_spec_path=args.job_spec,
        dataset_meta_path=args.dataset_meta,
        log_dir=args.log_dir,
    )

    print(result["status"])
    print(result.get("log_dir"))

```

这样 `train_gfn_v2.py` 不再自己组装 GFN。它只是命令行外壳。

# 四、不要改烂 alphasage：`alphagen` 是核心表达式体系，不能另写 AST

你特别提到 `src\expression\ast.py` 是否不必要。我同意你的判断：**当前分支能看到的表达式体系在** **`src/alphagen/data`** **下，包括** **`expression.py`、`tokens.py`、`tree.py`、`calculator.py`、`dimension.py`、`expression_knowledge_graph.py`。我没有在当前 GitHub 树里看到** **`src/expression/ast.py`** **作为正式模块。**([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src/alphagen/data "Finance_factor_digging/src/alphagen/data at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

因此，若本地或之前生成过 `src/expression/ast.py`，建议处理为：

```
结论：
- 不应作为主表达式系统。
- 不应让 GFN、loader、factor builder、screening 依赖它。
- 不应与 alphagen.data.expression 并存为两套 AST。

```

正确做法是把所有表达式相关引用收束到：

```
from alphagen.data.expression import (
    Expression,
    Feature,
    Ref,
    Add,
    Sub,
    Mul,
    Div,
    Rank,
    TsMean,
    TsStd,
    TsRank,
    TsDelta,
    TsCorr,
    TsCov,
    # ...
)

```

`mining/family_search_space.py` 当前就是从 `alphagen.data.expression` 导入 `Ref`、`TsMean`、`TsStd`、`TsRank`、`TsDelta`、`TsCorr`、`TsCov`、`Add`、`Sub`、`Mul`、`Div`、`Rank` 等 operator，并根据 `operator_whitelist`、`forbid_operators`、`delta_times`、`constants` 构造搜索空间。这个方向是对的，问题不是缺表达式系统，而是表达式系统引用应该唯一。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/family_search_space.py "Finance_factor_digging/src/mining/family_search_space.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

你应该在全项目做一次搜索：

```
grep -R "src.expression" -n src
grep -R "expression.ast" -n src
grep -R "class .*Node" -n src | head -50
grep -R "class .*AST" -n src

```

如果搜到 `src.expression.ast` 或新 AST 引用，按下面规则改：

```
1. GFN 环境、搜索空间、因子回放、筛选、loader 不允许 import src.expression.ast。
2. 如只是旧实验代码，删引用，不一定立刻删文件。
3. 如果有测试依赖它，测试也改到 alphagen.data.expression。
4. 如果有表达式字符串解析需求，优先使用 alphagen 现有 tokens/tree/expression 能力。
5. 不新增 parser，除非只是把字符串表达式转回 alphagen Expression。

```

这点非常重要。重复 AST 是量化因子系统里最容易制造隐性 bug 的地方：一个 AST 能 evaluate，另一个 AST 能 stringify，第三个 AST 能 serialize，最后 GFN 生成的表达式、回测表达式、缓存 key、导出表达式全不一致。

# 五、`alpha_gfn` 不能被绕开，不能新写 `AlphaGFNSearchAdapter`

`alpha_gfn/gflownet.py` 当前是对 `torchgfn.gflownet.TBGFlowNet` 的轻量扩展，定义了 `EntropyTBGFlowNet`，在构造函数中增加 `entropy_coef`、`entropy_temperature`，并在 `loss(...)` 中调用 `super().loss(...)` 后加入 entropy 相关项。它是非常小的 GFN 扩展层，不应该被重写。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/gflownet.py "Finance_factor_digging/src/alpha_gfn/gflownet.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`alpha_gfn/alpha_pool_v2.py` 当前定义的 `AlphaPoolGFN` 是继承 `alphagen.models.alpha_pool.AlphaPool` 的增强版本，构造参数包括 `capacity`、`stock_data`、`target`、`ic_lower_bound`、`l1_alpha`、`cache_manager`、`min_ic_threshold`、`max_similarity_threshold`、`entry_strategy`、`diversity_weight`、`novelty_decay`、`enable_cache` 等。它的 `try_new_expr(...)` 会 evaluate 表达式、计算 IC、根据 `entry_strategy` 决定是否进池。这个类已经是你们需要适配的地方，不需要新建 `AlphaGFNSearchAdapter`。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/alpha_pool_v2.py "Finance_factor_digging/src/alpha_gfn/alpha_pool_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`alpha_gfn/search_space.py` 已经有基础 `build_search_space(operator_names, delta_times, constants)`，会从 `alpha_gfn.config` 和 operator map 解析 operator、delta、constant。`alpha_gfn/search_space_v2.py` 进一步支持 `family_spec`，说明这个方向已经为 YAML 因子族准备过扩展。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/search_space.py "Finance_factor_digging/src/alpha_gfn/search_space.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

因此，你不应该新定义：

```
class AlphaGFNSearchAdapter:
    ...

```

因为它会产生一个额外概念层，让调用关系变成：

```
mining -> adapter -> alpha_gfn -> alphagen

```

这没有必要。正确关系应该是：

```
mining 直接组装 alpha_gfn 需要的对象

```

也就是：

```
operators, delta_times, constants = build_family_search_space(family_spec)

pool = AlphaPoolGFN(
    capacity=job_spec.pool_capacity,
    stock_data=train_loader,
    target=target_expression,
    entry_strategy=job_spec.raw.get("entry_strategy", "ic_ranking"),
    diversity_weight=job_spec.raw.get("diversity_weight", 0.3),
    min_ic_threshold=job_spec.raw.get("min_ic_threshold", 0.05),
    max_similarity_threshold=job_spec.raw.get("max_similarity_threshold", 0.95),
    enable_cache=job_spec.raw.get("enable_cache", True),
    cache_manager=cache_manager,
)

env = GFNEnvCore(
    operators=operators,
    features=feature_list_or_enum,
    delta_times=delta_times,
    constants=constants,
    max_expr_length=job_spec.max_expr_length,
    pool=pool,
)

```

重点不是再包一层 adapter，而是让 `MiningContext` 产出这几个对象：

```
context.train_loader
context.test_loader
context.feature_enum
context.target_expression
context.operators
context.delta_times
context.constants
context.pool
context.env
context.gfn
context.sampler

```

当前 `MiningContext` 已经产出 `train_loader`、`test_loader`、`target_expression`、`operators`、`delta_times`、`constants`，只差把 GFN 训练链补齐。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/mine_factors.py "Finance_factor_digging/src/mining/mine_factors.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

# 六、当前最危险的 import 问题：`alpha_gfn.env.core` 需要核对

`train_gfn.py` 原始内容中使用了 `from alpha_gfn.env.core import GFNEnvCore`。但当前 GitHub 页面展示的 `src/alpha_gfn` 目录文件包括 `__init__.py`、`alpha_pool.py`、`alpha_pool_v2.py`、`cache_manager.py`、`config.py`、`gflownet.py`、`modules.py`、`preprocessors.py`、`search_space.py`、`search_space_v2.py`，没有在该目录列表里看到 `env/` 子目录。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/refs/heads/feature/non-data-progress-second/src/train_gfn.py "raw.githubusercontent.com"))

这个点必须作为 P0 问题处理，因为它会导致：

```
ModuleNotFoundError: No module named 'alpha_gfn.env'

```

如果本地确实有 `src/alpha_gfn/env/core.py` 但 GitHub 页面没显示，那先确认是否未提交。若没有，则不能新写一个“大而全 adapter”，而应该恢复/放回原 alphasage 的 `GFNEnvCore` 实现，或者把 import 改到真实存在的环境类。

建议检查：

```
find src/alpha_gfn -maxdepth 3 -type f | sort
grep -R "class GFNEnvCore" -n src
grep -R "GFNEnvCore" -n src

```

修改规则：

```
如果 class GFNEnvCore 已经存在于其他文件：
    改 import，不复制实现。

如果 class GFNEnvCore 不存在：
    从原 alphasage/alpha_gfn 项目恢复最小 env/core.py。
    不要写新的 AlphaGFNSearchAdapter。
    不要把 env 逻辑塞到 mining.mine_factors.py。

```

目标文件结构应该是：

```
src/alpha_gfn/env/__init__.py
src/alpha_gfn/env/core.py

```

但这里的 `core.py` 只能做 GFN 环境该做的事：

```
- 接收 feature tokens / operator tokens / delta tokens / constant tokens
- 维护 action mask
- 把 action sequence 转成 alphagen.data.expression.Expression
- 计算 reward 时调用 AlphaPoolGFN.try_new_expr(...)
- 返回 torchgfn 需要的 states / transitions / terminal info

```

它不应该做：

```
- 读取 parquet
- 解析 YAML
- 处理期货/期权字段
- 维护 job spec
- 处理 factor registry
- 新建 AST

```

这就是“适配给 alphasage”，而不是“改造 alphasage”。

# 七、数据读取问题：`DatasetMeta` 已经有方向，但 loader 仍有硬编码残留

`DatasetMeta` 当前已经定义了比较完整的元数据框架。它的必填字段包括 `dataset_id`、`name`、`frequency`、`domain`、`data_dir`、`files`、`columns`、`date_range`；可选字段包括 `version`、`region`、`market`、`asset_type`、`freq_group`、`timezone`、`calendar`、`sample_pool`、`supported_operators`、`max_ast_depth`、`recommended_delta_times`、`recommended_constants`、`layers_enabled`、`operator_whitelist` 等。并且它的有效市场/资产类型里已经有 futures、options、fx、crypto 等方向。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/dataset_meta.py "Finance_factor_digging/src/alphagen_generic/dataset_meta.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

但是 `ParquetFeatureLoader` 仍然有明显历史包袱：它对 A/B/C/E 有硬编码 file map，优先 filled path，否则 raw path，还在股票日频目标上有 daily close merge 的特殊逻辑。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/parquet_feature_loader.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`ParquetFeatureLoaderV2` 已经明显更接近正确方向：构造参数里支持 `dataset_meta`、`dataset_id`、`freq_group`、`layers`、`feature_names`、`segment_name`、`read_mode`、`cache_root`、`atomic_path`、`feature_file_map_raw`、`feature_file_map_filled` 等；读取时也有 `_build_data_view`、`_resolve_input_files`、raw/filled/atomic/mixed 层构建逻辑，并支持按 suffix 查找 `*_robust`、`*_valid`、`*_raw` 或原始 feature 列。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

当前问题不是没有 V2 loader，而是：

```
1. V1 loader 仍被 train_gfn.py 使用。
2. V2 loader 内部仍保留 A/B/C/E 默认 file map。
3. V2 loader 的 mixed 逻辑是 filled > raw > atomic，但“atomic”在因子搜索中未必应该是最后 fallback。
4. 目标表达式仍默认 Feature(CLOSE)，不适配期货 settle、外汇 mid、宏观 value。
5. DatasetMeta 的字段能力没有被 mine_factors 严格使用。

```

# 九、`FeatureRegistryManagerV2` 要成为唯一字段枚举来源

`FeatureRegistryManagerV2` 当前已经支持 raw 与 atomic 两层，提供 `get_features_by_domain_and_layer(domain, layer, status_filter)`、`get_features_by_domain(...)`、`create_feature_enum(...)`、`create_feature_enum_by_layer(...)` 等能力。它还会把 atomic 特征加 `atomic_` 前缀以避免冲突。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/feature_registry_manager_v2.py "Finance_factor_digging/src/alphagen_generic/feature_registry_manager_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

这里的方向基本正确，但要改两个细节。

## 9.1 不要让 loader 自己猜 feature list

当前 `ParquetFeatureLoaderV2` 支持 `feature_names`，但实际很多时候还是从 registry 和 layer 推断。你应该明确规定：

```
FeatureRegistryManagerV2 是唯一 feature list 来源；
DatasetMeta 只描述文件和列名；
factor_family 只描述哪些 layer、哪些 operator、哪些 feature category 可用；
loader 只读取被 registry/family/job 共同筛出的 feature_names。

```

最终的 feature 决策流程应该是：

```
def resolve_feature_names(job_spec, dataset_meta, family_spec, registry_manager):
    layers = family_spec.get("enabled_layers", dataset_meta.layers_enabled)

    feature_names = []
    for layer in layers:
        if layer in ("raw", "filled"):
            feature_names.extend(
                registry_manager.get_features_by_domain_and_layer(
                    dataset_meta.domain,
                    "raw",
                    job_spec.status_filter,
                )
            )
        elif layer == "atomic":
            atomic = registry_manager.get_features_by_domain_and_layer(
                dataset_meta.domain,
                "atomic",
                job_spec.status_filter,
            )
            feature_names.extend([f"atomic_{x}" for x in atomic])

    include = family_spec.get("include_features")
    exclude = family_spec.get("exclude_features", [])

    if include:
        feature_names = [x for x in feature_names if x in include]

    feature_names = [x for x in feature_names if x not in exclude]
    return sorted(set(feature_names))

```

## 9.2 `CLOSE` 不能永远写死

`FeatureRegistryManagerV2.create_feature_enum(...)` 当前固定 `enum_dict = {'CLOSE': 0}`，目的是保留 CLOSE 作为目标计算。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/feature_registry_manager_v2.py "Finance_factor_digging/src/alphagen_generic/feature_registry_manager_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

股票日频中这没问题，但期货可能 target 用 `settle`，外汇可能 target 用 `mid`，宏观可能 target 用 `value`。你不应该在 `alpha_gfn` 里改这个，而应该在 `DatasetMeta` 增加 target 字段，然后在 `MiningContext._build_target_expression()` 中解析：

当前 `MiningContext._build_target_expression()` 是：

```
feature_enum = registry_manager.create_feature_enum(domain, self.job_spec.status_filter, layers)

close = Feature(feature_enum.CLOSE)
target = Ref(close, -self.job_spec.label_days) / close - 1

```

这个对 A 股 close 很直接，但对多资产不够。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/mine_factors.py "Finance_factor_digging/src/mining/mine_factors.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

应改成：

```
def _build_target_expression(self) -> Expression:
    registry_manager = self.registry_manager
    layers = self.family_spec.get("enabled_layers", self.dataset_meta.layers_enabled)
    domain = self.dataset_meta.domain

    feature_enum = registry_manager.create_feature_enum(
        domain,
        self.job_spec.status_filter,
        layers,
    )

    target_cfg = self.dataset_meta.raw.get("target", {})
    price_col = target_cfg.get("price_column", "close")
    enum_name = target_cfg.get("feature_enum", price_col).upper()

    if not hasattr(feature_enum, enum_name):
        fallback = target_cfg.get("fallback_price_columns", [])
        found = None
        for col in fallback:
            if hasattr(feature_enum, col.upper()):
                found = col.upper()
                break
        if found is None:
            raise ValueError(
                f"Target feature {enum_name} not found in feature_enum. "
                f"Available: {[x.name for x in feature_enum]}"
            )
        enum_name = found

    base = Feature(getattr(feature_enum, enum_name))
    target_type = target_cfg.get("expression", "forward_return")
    horizon = int(target_cfg.get("label_days", self.job_spec.label_days))

    if target_type == "forward_return":
        return Ref(base, -horizon) / base - 1
    elif target_type == "forward_change":
        return Ref(base, -horizon) - base
    elif target_type == "forward_log_return":
        return Log(Ref(base, -horizon) / base)
    else:
        raise ValueError(f"Unsupported target expression: {target_type}")

```

这里的重点是：**目标表达式是 mining 层根据 dataset\_meta 组装出来的，不是 alpha\_gfn 或 alphagen 核心硬编码。**

# 十、`ParquetFeatureLoaderV2` 的修改重点：去硬编码，保留兼容默认值

`ParquetFeatureLoaderV2` 已经有 `_resolve_input_files()` 和 `_build_data_view()`，并支持 `raw`、`filled`、`atomic`、`mixed` 读取。当前最应该做的是让 `DatasetMeta.files` 成为第一优先级。已有逻辑已经朝这个方向走，但 A/B/C/E 默认 maps 仍然会干扰长期清晰性。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

建议修改原则：

```
1. dataset_meta.files 存在时，只按 dataset_meta.files 读。
2. CLI 传入 feature_file_map_* 时，作为显式 override。
3. 老的 A/B/C/E hard-coded map 只作为 legacy fallback。
4. loader 不再根据 domain 猜资产类型。
5. loader 不负责决定 enabled_layers，只按传入 layers 读。

```

当前 V2 loader 构造参数已经包括：

```
domain
start_time
end_time
registry_manager
dataset_meta
data_dir
daily_path
pool_path
device
max_backtrack_days
status_filter
use_filled
feature_file_map_raw
feature_file_map_filled
atomic_path
columns
dataset_id
freq_group
layers
feature_names
segment_name
read_mode
cache_root
return_close_only

```

这足够，不需要再新建 loader。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/parquet_feature_loader_v2.py "Finance_factor_digging/src/alphagen_generic/parquet_feature_loader_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

你应改的是 `_resolve_input_files()` 的优先级，示意：

```
def _resolve_input_files(self) -> Dict[str, List[Path]]:
    """
    返回:
    {
        "raw": [...],
        "filled": [...],
        "atomic": [...]
    }
    """
    files = {"raw": [], "filled": [], "atomic": []}

    # 1. DatasetMeta first
    if self.dataset_meta is not None:
        meta_files = self.dataset_meta.raw.get("files", {})
        for layer in ("raw", "filled", "atomic"):
            layer_files = meta_files.get(layer, {})
            if isinstance(layer_files, dict):
                for _, rel_path in layer_files.items():
                    files[layer].append(self.data_dir / rel_path)
            elif isinstance(layer_files, list):
                for rel_path in layer_files:
                    files[layer].append(self.data_dir / rel_path)
            elif isinstance(layer_files, str):
                files[layer].append(self.data_dir / layer_files)

    # 2. Explicit constructor overrides
    if self.feature_file_map_raw:
        files["raw"].extend(Path(x) for x in self.feature_file_map_raw.values())

    if self.feature_file_map_filled:
        files["filled"].extend(Path(x) for x in self.feature_file_map_filled.values())

    if self.atomic_path:
        files["atomic"].append(Path(self.atomic_path))

    # 3. Legacy fallback only when nothing configured
    if not any(files.values()):
        files = self._legacy_resolve_abce_files()

    # 4. Filter by self.layers
    return {
        layer: paths
        for layer, paths in files.items()
        if layer in self.layers and paths
    }

```

同时 `_build_data_view()` 不应默认 `filled > raw > atomic`。这里要区分两件事：

```
filled 是 raw 的清洗版本；
atomic 是额外生成的字段层；
它们不是简单互相替代关系。

```

更合理的语义是：

```
read_mode = "raw_only"      -> 只读 raw
read_mode = "filled_only"   -> 只读 filled
read_mode = "atomic_only"   -> 只读 atomic
read_mode = "stack"         -> 按 feature_names 同时读多个 layer，列名不冲突
read_mode = "prefer_filled" -> 同名字段 filled 覆盖 raw，atomic 另保留 atomic_ 前缀

```

建议默认改为：

```
read_mode: prefer_filled
layers_enabled: [filled, atomic]

```

而不是把 atomic 当 fallback。

# 十一、`mining/family_search_space.py` 与 `alpha_gfn/search_space_v2.py` 的关系要收清楚

当前有三个地方可能构造搜索空间：

```
alpha_gfn/search_space.py
alpha_gfn/search_space_v2.py
mining/family_search_space.py

```

`alpha_gfn/search_space.py` 是基础版，按 operator\_names、delta\_times、constants 构造。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/search_space.py "Finance_factor_digging/src/alpha_gfn/search_space.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`alpha_gfn/search_space_v2.py` 支持 `family_spec`，显然是想对接因子族配置。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/search_space_v2.py "Finance_factor_digging/src/alpha_gfn/search_space_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

`mining/family_search_space.py` 则从 `family_spec` 读取 `operator_whitelist`、`forbid_operators`、`delta_times`、`constants`，并直接从 `alphagen.data.expression` 组装 operator map。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/family_search_space.py "Finance_factor_digging/src/mining/family_search_space.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

三者并存会导致“到底哪个 operator map 生效”的问题。我的建议是：

```
短期不大改：
- 保留 mining.family_search_space.build_family_search_space(...) 作为 mining 层入口。
- 它内部尽量调用 alpha_gfn.search_space_v2.build_search_space(...)。
- 如果 search_space_v2 不满足，再保留当前 operator_map 作为 fallback。

中期收敛：
- alpha_gfn.search_space_v2 负责 operator 解析。
- mining.family_search_space 只负责读取/校验 family_spec，不直接维护 operator_map。

```

推荐改成：

```
# src/mining/family_search_space.py

def build_family_search_space(family_spec: Dict[str, Any]) -> Tuple[List, List, List]:
    errors = validate_family_spec(family_spec)
    if errors:
        raise ValueError(f"Invalid family spec: {errors}")

    from alpha_gfn.search_space_v2 import build_search_space

    operator_names = family_spec.get("operator_whitelist")
    delta_times = family_spec.get("delta_times")
    constants = family_spec.get("constants")

    operators, deltas, consts = build_search_space(
        operator_names=operator_names,
        delta_times=delta_times,
        constants=constants,
        family_spec=family_spec,
    )

    forbid = set(family_spec.get("forbid_operators", []))
    if forbid:
        operators = [
            op for op in operators
            if getattr(op, "__name__", op.__class__.__name__) not in forbid
        ]

    return operators, deltas, consts

```

这样 `mining` 仍是入口，但 operator 真正解析归 `alpha_gfn`。这不是新写系统，是把已有系统接好。

# 十二、`mine_factors.py` 应补齐的不是新框架，而是 GFN 训练闭环

当前 `mine_factors.py` 的 `mine_factors(...)` 已经创建 `AlphaPoolGFN`，但没有真正启动 GFN sampler/training，只返回 initialized。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/mine_factors.py "Finance_factor_digging/src/mining/mine_factors.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

建议 `MiningContext` 增加这些属性：

```
class MiningContext:
    def __init__(...):
        self.device = self._resolve_device()
        self.registry_manager = self._build_registry_manager()
        self.feature_enum = self._build_feature_enum()
        self.feature_names = self._resolve_feature_names()

        self.target_expression = self._build_target_expression()
        self.operators, self.delta_times, self.constants = self._build_search_space()

        self.pool = self._build_pool()
        self.env = self._build_env()
        self.encoder = self._build_encoder()
        self.gfn = self._build_gfn()
        self.sampler = self._build_sampler()

```

但注意：这不是新文件，只是把 `mine_factors.py` 里的 `MiningContext` 补完整。

`mine_factors(...)` 应该变成：

```
def mine_factors(job_spec_path: str, dataset_meta_path: Optional[str] = None,
                 log_dir: Optional[str] = None, **kwargs) -> Dict[str, Any]:
    context = build_mining_context(job_spec_path, dataset_meta_path, log_dir)

    for episode in range(context.job_spec.n_episodes):
        trajectories = context.sampler.sample_trajectories(
            n_trajectories=context.job_spec.raw.get("batch_size", 16)
        )

        loss = context.gfn.loss(context.env, trajectories)

        context.optimizer.zero_grad()
        loss.backward()
        context.optimizer.step()

        if episode % context.job_spec.log_freq == 0:
            pool_stats = context.pool.get_stats() if hasattr(context.pool, "get_stats") else {}
            metrics = {
                "loss": float(loss.detach().cpu()),
                "pool_size": len(context.pool.exprs) if hasattr(context.pool, "exprs") else None,
            }
            context.logger.log_checkpoint(episode, pool_stats, metrics)

    final = context.pool.export_pool() if hasattr(context.pool, "export_pool") else {}
    context.logger.log_completion(final)

    return {
        "status": "completed",
        "log_dir": context.log_dir,
        "pool": final,
    }

```

上面只是结构示意。实际 `torchgfn` 的 sampler API 以当前项目中 `train_gfn.py` 的可运行写法为准。重点是：**训练闭环应该搬到** **`mining.mine_factors`，不是继续在** **`train_gfn.py`** **扩展。**

# 十三、`DatasetMeta` 默认值不能偷偷创建 A 股数据集

# 十六、`FeatureRegistryManagerV2` 与原子字段 YAML 的落地关系

现在 `FeatureRegistryManagerV2` 似乎以 DataFrame/CSV 形式管理 raw 与 atomic feature，并通过 `allow_in_alphaprobe` 形成 status map。它还支持 `add_atomic_feature(...)`。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/feature_registry_manager_v2.py "Finance_factor_digging/src/alphagen_generic/feature_registry_manager_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

建议你不要让 atomic YAML 直接被 GFN 读取，而是走：

```
atomic_fields.yaml
    -> data_prep.build_atomic_features.py
        1. 生成 atomic parquet
        2. 生成/更新 atomic feature registry
    -> FeatureRegistryManagerV2 读取 registry
    -> loader 读取 atomic parquet
    -> GFN 看到 atomic_xxx feature

```

也就是：

```
YAML 是数据准备输入；
registry 是搜索输入；
parquet 是计算输入。

```

不要让一个 YAML 同时承担“字段定义 + 计算逻辑 + 搜索空间 + 数据路径 + 任务参数”。那会变成新的混乱中心。

建议 atomic registry 的字段至少是：

```
feature_name,domain,layer,category,description,formula,source_cols,fill_policy,allow_in_alphaprobe,status
ret_1,FUT,atomic,return,1 day return,pct_change(close,1),close,none,1,active
oi_chg_1,FUT,atomic,open_interest,1 day OI change,diff(open_interest,1),open_interest,none,1,active

```

在 `FeatureRegistryManagerV2.get_features_by_domain_and_layer(...)` 里，目前 atomic 的 key 是 `f"{domain}:{feature}:atomic"`，raw 是 `f"{domain}:{feature}"`，这个可以保留。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alphagen_generic/feature_registry_manager_v2.py "Finance_factor_digging/src/alphagen_generic/feature_registry_manager_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

但 `update_feature_status(...)` 当前如果 key 写成 `f"{feature_name}:{layer}"`，与前面的 status key 格式不一致，就需要统一。建议统一为：

```
def _status_key(self, domain: str, feature_name: str, layer: str) -> str:
    if layer == "raw":
        return f"{domain}:{feature_name}"
    return f"{domain}:{feature_name}:{layer}"

```

然后所有 status map 都调用这个函数。

`MiningContext._build_target_expression()` 目前默认 `feature_enum.CLOSE`。这对股票可跑，但对多资产会成为隐性失败点。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/mining/mine_factors.py "Finance_factor_digging/src/mining/mine_factors.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

enum_dict = {}

target_feature_name = (

这里 `CLOSE` 可以继续作为兼容别名，但不能再是唯一真实字段。

# 十九、`alpha_pool_v2` 的使用：配置它，不要改造它

`AlphaPoolGFN.try_new_expr(...)` 已经承担了表达式评估、缓存、IC 计算、novelty/diversity 判断、entry strategy 等职责。它还提供 `_add_factor(...)`、`_swap_idx(...)`、`export_pool(...)` 等能力。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/alpha_pool_v2.py "Finance_factor_digging/src/alpha_gfn/alpha_pool_v2.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

因此，不要在外面写：

```
class AlphaGFNSearchAdapter:
    def evaluate_expr(...)
    def add_to_pool(...)
    def compute_ic(...)

```

这会复制 `AlphaPoolGFN` 的职责。

正确改法是把 `job_spec` 的参数明确传进去：

```
pool = AlphaPoolGFN(
    capacity=context.job_spec.pool_capacity,
    stock_data=context.train_loader,
    target=context.target_expression,
    ic_lower_bound=context.job_spec.raw.get("ic_lower_bound", None),
    l1_alpha=context.job_spec.raw.get("l1_alpha", 0.0),
    cache_manager=context.cache_manager,
    min_ic_threshold=context.job_spec.raw.get("min_ic_threshold", 0.05),
    max_similarity_threshold=context.job_spec.raw.get("max_similarity_threshold", 0.95),
    entry_strategy=context.job_spec.raw.get("entry_strategy", "ic_ranking"),
    diversity_weight=context.job_spec.raw.get("diversity_weight", 0.3),
    novelty_decay=context.job_spec.raw.get("novelty_decay", 0.99),
    enable_cache=context.job_spec.raw.get("enable_cache", True),
)

```

这里如果 `cache_manager` 的 key 构造和 `AlphaPoolGFN` 调用不匹配，不要在 pool 外再包一层。应该在 `cache_manager.py` 内补一个兼容方法，比如：

```
class CacheManager:
    def build_key(self, expr, dataset_id=None, segment_name=None, start_time=None, end_time=None):
        ...

```

或者：

```
def get_or_compute(self, expr, compute_fn, **context):
    key = self.build_key(expr, **context)
    ...

```

这样 pool 仍然是 pool，cache 仍然是 cache。

# 二十八、一个具体的 `mine_factors.py` 内部修改草案

以下是结构草案，重点是告诉你如何改现有代码，而不是让你新建一堆文件。

```
class MiningContext:
    """Canonical context for one mining job."""

    def __init__(self, job_spec, family_spec, dataset_meta, log_dir):
        self.job_spec = job_spec
        self.family_spec = family_spec
        self.dataset_meta = dataset_meta
        self.log_dir = log_dir

        self.device = self._resolve_device()

        self.registry_manager = self._build_registry_manager()
        self.layers = self._resolve_layers()
        self.feature_names = self._resolve_feature_names()
        self.feature_enum = self._build_feature_enum()

        self.train_loader, self.test_loader = self._build_data_loaders()
        self.target_expression = self._build_target_expression()
        self.operators, self.delta_times, self.constants = self._build_search_space()

        self.cache_manager = self._build_cache_manager()
        self.pool = self._build_pool()
        self.env = self._build_env()
        self.encoder = self._build_encoder()
        self.gfn = self._build_gfn()
        self.sampler = self._build_sampler()
        self.optimizer = self._build_optimizer()

    def _resolve_device(self):
        cuda_idx = int(self.job_spec.raw.get("cuda", 0))
        if torch.cuda.is_available() and cuda_idx >= 0:
            return torch.device(f"cuda:{cuda_idx}")
        return torch.device("cpu")

    def _build_registry_manager(self):
        return FeatureRegistryManagerV2(
            # 尽量从 config/datahub 或 dataset_meta 指定路径读取
            # 不要在这里写死 test_registry
        )

    def _resolve_layers(self):
        family_layers = self.family_spec.get("enabled_layers")
        dataset_layers = self.dataset_meta.raw.get("layers_enabled", ["raw"])

        if family_layers:
            missing = set(family_layers) - set(dataset_layers)
            if missing:
                raise ValueError(f"Family requires missing dataset layers: {missing}")
            return family_layers

        return dataset_layers

    def _resolve_feature_names(self):
        names = []
        for layer in self.layers:
            if layer == "filled":
                # filled 对 registry 来说通常仍对应 raw 特征名
                layer_for_registry = "raw"
            else:
                layer_for_registry = layer

            feats = self.registry_manager.get_features_by_domain_and_layer(
                self.dataset_meta.domain,
                layer_for_registry,
                self.job_spec.status_filter,
            )

            if layer_for_registry == "atomic":
                feats = [f"atomic_{x}" for x in feats]

            names.extend(feats)

        include = self.family_spec.get("include_features")
        exclude = set(self.family_spec.get("exclude_features", []))

        if include:
            names = [x for x in names if x in include]

        names = [x for x in names if x not in exclude]
        return sorted(set(names))

    def _build_feature_enum(self):
        return self.registry_manager.create_feature_enum(
            self.dataset_meta.domain,
            self.job_spec.status_filter,
            self.layers,
        )

    def _build_data_loaders(self):
        common_kwargs = dict(
            domain=self.dataset_meta.domain,
            registry_manager=self.registry_manager,
            dataset_meta=self.dataset_meta,
            device=self.device,
            max_backtrack_days=self.job_spec.max_backtrack_days,
            max_future_days=self.job_spec.max_future_days,
            status_filter=self.job_spec.status_filter,
            use_filled=self.job_spec.raw.get("use_filled", True),
            layers=self.layers,
            feature_names=self.feature_names,
            segment_name=self.job_spec.segment_name,
            read_mode=self.job_spec.raw.get("read_mode", "prefer_filled"),
            cache_root=self.job_spec.raw.get("cache_root", "data/cache"),
        )

        train_loader = ParquetFeatureLoaderV2(
            start_time=self.job_spec.train_start,
            end_time=self.job_spec.train_end,
            **common_kwargs,
        )

        test_loader = ParquetFeatureLoaderV2(
            start_time=self.job_spec.test_start,
            end_time=self.job_spec.test_end,
            **common_kwargs,
        )

        return train_loader, test_loader

    def _build_target_expression(self):
        target_cfg = self.dataset_meta.raw.get("target", {})
        price_name = target_cfg.get("feature_name") or target_cfg.get("price_column", "close")
        enum_name = price_name.upper()

        if not hasattr(self.feature_enum, enum_name):
            fallback = target_cfg.get("fallback_price_columns", [])
            for col in fallback:
                if hasattr(self.feature_enum, col.upper()):
                    enum_name = col.upper()
                    break
            else:
                if hasattr(self.feature_enum, "CLOSE"):
                    enum_name = "CLOSE"
                else:
                    raise ValueError(
                        f"Cannot resolve target feature {price_name}; "
                        f"available enum names: {[x.name for x in self.feature_enum]}"
                    )

        base = Feature(getattr(self.feature_enum, enum_name))
        horizon = int(target_cfg.get("label_days", self.job_spec.label_days))
        expr_type = target_cfg.get("expression", "forward_return")

        if expr_type == "forward_return":
            return Ref(base, -horizon) / base - 1
        if expr_type == "forward_change":
            return Ref(base, -horizon) - base
        if expr_type == "forward_log_return":
            return Log(Ref(base, -horizon) / base)

        raise ValueError(f"Unsupported target expression: {expr_type}")

    def _build_search_space(self):
        return build_family_search_space(self.family_spec)

    def _build_pool(self):
        return AlphaPoolGFN(
            capacity=self.job_spec.pool_capacity,
            stock_data=self.train_loader,
            target=self.target_expression,
            entry_strategy=self.job_spec.raw.get("entry_strategy", "ic_ranking"),
            diversity_weight=self.job_spec.raw.get("diversity_weight", 0.3),
            min_ic_threshold=self.job_spec.raw.get("min_ic_threshold", 0.05),
            max_similarity_threshold=self.job_spec.raw.get("max_similarity_threshold", 0.95),
            enable_cache=self.job_spec.raw.get("enable_cache", True),
            cache_manager=self.cache_manager,
        )

```

这类改法的好处是：**没有新增大模块，只是把当前散落在脚本中的逻辑收进已有** **`MiningContext`。**

# 二十九、`EntropyTBGFlowNet` 的一个小心点：检查 entropy loss 符号，不要重写

`alpha_gfn/gflownet.py` 当前 `EntropyTBGFlowNet.loss(...)` 是先调用 `super().loss(...)` 得到 base loss，再计算 entropy bonus，然后合成 total loss。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-second/src/alpha_gfn/gflownet.py "Finance_factor_digging/src/alpha_gfn/gflownet.py at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

这里建议你只做一件事：检查符号是否符合你们的训练目标。

常见语义是：

```
如果 entropy 是鼓励探索的 bonus，优化 loss 时通常是 base_loss - coef * entropy。
如果代码写成 base_loss + coef * entropy，则可能是在惩罚高熵。

```

但不要因此重写 GFN。你只需要：

```
# alpha_gfn/gflownet.py

if self.entropy_as_bonus:
    total_loss = base_loss - self.entropy_coef * entropy_bonus
else:
    total_loss = base_loss + self.entropy_coef * entropy_bonus

```

或者更保守：

```
entropy_loss_sign = config.get("entropy_loss_sign", -1.0)
total_loss = base_loss + entropy_loss_sign * self.entropy_coef * entropy_bonus

```

这个属于“小参数化修复”，不是架构重写。

GFN 搜索表达式时把它们当 feature。

## 31.3 指数

指数相对简单，只要 code/date/close/volume/amount 可读。行业指数、宽基指数可以通过 sample\_pool 控制。

## 31.4 外汇

外汇的 price column 可能是 mid。不要假设 close。通过：

```
target:
  price_column: mid
  fallback_price_columns: [close]

```

解决。

## 31.5 宏观

宏观数据通常低频、非横截面、缺失多。短期不要把宏观直接塞到横截面 GFN 里；先做成可 join 的外生字段或单独 domain：

```
方案 A：宏观作为 market-wide feature，按 date broadcast 到所有 instruments。
方案 B：宏观单独挖掘时间序列因子。

```

最小实现建议先做方案 A：

```
join_policy:
  macro:
    method: asof
    direction: backward
    broadcast_to_instruments: true

```

这个 join 应该在 `ParquetFeatureLoaderV2` 或数据预处理层完成，不应在 GFN 中完成。

# 三十三、哪些东西不要做

这里要非常明确。

## 33.1 不要新建 `AlphaGFNSearchAdapter`

理由：`AlphaPoolGFN`、`GFNEnvCore`、`EntropyTBGFlowNet`、`build_search_space` 本来就是 GFN 搜索链。新 adapter 只会复制职责。

## 33.2 不要新建 `src/expression/ast.py`

理由：`alphagen.data.expression`、`tokens.py`、`tree.py` 已经是表达式核心。当前分支树也显示表达式系统在 `alphagen/data` 下。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second/src/alphagen/data "Finance_factor_digging/src/alphagen/data at feature/non-data-progress-second · 789453/Finance_factor_digging · GitHub"))

## 33.3 不要把期货/期权/FX 写进 `alpha_gfn`

理由：GFN 不应该知道资产类型。资产差异由 `DatasetMeta`、`FeatureRegistryManagerV2`、`ParquetFeatureLoaderV2`、`data_prep` 处理。

## 33.4 不要同时维护 V1/V2 两条新逻辑

理由：`ParquetFeatureLoader` 与 `ParquetFeatureLoaderV2` 并存可以，但新流程只走 V2。V1 只 legacy。

## 33.5 不要把 `job_spec`、`dataset_meta`、`factor_family` 合成一个超级 YAML

理由：三者变更频率不同。数据集配置、搜索空间配置、单次任务配置必须分开。

## 33.6 不要在 `build_digged_factors.py` 里重新训练或搜索

理由：它只做 replay/export。

# 三十六、最终结论

这个项目不缺“更多代码”，缺的是**唯一主线**。当前分支已经有足够多的正确组件：`MiningJobSpec`、`MiningContext`、`DatasetMeta`、`FeatureRegistryManagerV2`、`ParquetFeatureLoaderV2`、`family_search_space`、`AlphaPoolGFN`、`EntropyTBGFlowNet`、`alphagen.data.expression`。你现在要做的是把这些组件按一条固定链路接起来，而不是继续引入新的 AST、新 adapter、新 runner、新抽象层。当前 README 和工程文档已经把 raw/filled/atomic、YAML 因子族、job spec、loader V2 的方向写出来了；代码里也已经有对应模块，只是入口和职责没有收束。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-second "GitHub - 789453/Finance_factor_digging at feature/non-data-progress-second · GitHub"))

最重要的三条改造原则是：

```
1. alphasage / alphagen / alpha_gfn 是核心能力层，只做小补丁，不重写。
2. 多资产、多字段、多数据层全部通过 DatasetMeta + FeatureRegistry + ParquetFeatureLoaderV2 + YAML 适配。
3. mining.mine_factors 是唯一新流程入口；train_gfn.py/train_gfn_v2.py 不再平行发展。

```

这样改完后，系统的“最后 10%”才会从“靠猜测拼模块”变成“按 job spec 组装对象、按 dataset meta 读取数据、按 factor family 构造搜索空间、按 alpha\_gfn 执行搜索、按 alphagen 表达式回放结果”。这才是清晰、适配、有效、准确的收束方式。
