# 2. 当前代码的主要冗余和不统一问题

## 2.1 `mine_factors.py` 是最大耦合点：应拆成 orchestrator + GFN engine

`src/mining/mine_factors.py` 当前标题写的是 “AlphaPROBE Factor Mining Pipeline”，但说明里又写 “Follows the AlphaSage / AlphaGFN research paradigm”。代码直接 import `AlphaPoolGFN`、`GFNEnvCore`、`SequenceEncoder`、`EntropyTBGFlowNet`、`Sampler`、`DiscretePolicyEstimator` 等 GFN 专属对象。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/feature/non-data-progress-fourth-425/src/mining/mine_factors.py "raw.githubusercontent.com"))

这会导致一个结构性问题：

```
标准挖掘任务 = GFN 任务
标准输入 = GFN 需要的数据格式
标准输出 = AlphaPoolGFN.export_pool
标准评估 = AlphaPoolGFN 内部 try_new_expr 里的评估

```

这和你现在的目标冲突。你希望中间挖掘端未来可以是：

```
simple_llm
cogalpha
pysr
alphasage
alphaprobe
gfn
random_baseline
manual_formula

```

那么 `mine_factors.py` 不应该直接构建 GFN，而应该只做：

```
读取 JobSpec
读取 DatasetSpec
读取 UniverseSpec
构建 FactorContext
根据 engine.type 加载对应引擎
engine.discover(context) -> FactorCandidateBatch
统一检测、评估、导出

```

### 具体问题位置

当前 `mine_factors.py` 里 `MiningRuntimeContext` 直接包含：

```
pool: AlphaPoolGFN
env: GFNEnvCore
gfn: EntropyTBGFlowNet
sampler: TorchGFNCompatSampler
optimizer: torch.optim.Optimizer

```

这说明 runtime context 已经被 GFN 污染。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/feature/non-data-progress-fourth-425/src/mining/mine_factors.py "raw.githubusercontent.com"))

### 修改目标

把当前：

```
src/mining/mine_factors.py

```

拆成：

```
src/mining/orchestrator.py          # 与引擎无关的任务调度
src/mining/context.py               # FactorMiningContext 数据结构
src/mining/engine_registry.py       # 引擎注册和加载
src/mining/run_mining.py            # CLI 入口

src/engines/base.py                 # MiningEngine 抽象接口
src/engines/gfn_engine.py           # 当前 GFN 逻辑迁移到这里
src/engines/llm_engine.py           # 预留
src/engines/pysr_engine.py          # 预留
src/engines/cogalpha_engine.py      # 预留
src/engines/alphaprobe_engine.py    # 预留
src/engines/random_engine.py        # baseline

```

## 2.3 `AlphaPoolGFN` 既做 pool，又做评估，又做去重，又做输出：职责过重

`AlphaPoolGFN.try_new_expr()` 当前已经做了很多事：表达式质量验证、canonical hash 去重、表达式求值、value sanity、train metrics、valid metrics、池内相关性、semantic embedding 去重、composite score、入池替换。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-fourth-425/src/alpha_gfn/alpha_pool_v2.py "Finance_factor_digging/src/alpha_gfn/alpha_pool_v2.py at feature/non-data-progress-fourth-425 · 789453/Finance_factor_digging · GitHub"))

这在 GFN 训练阶段可以工作，但平台层不应该把这些逻辑锁死在 `AlphaPoolGFN` 里。原因很简单：如果明天 PySR 生成了 500 个表达式，也需要同样的检测和入池；如果 LLM 生成了 1000 个表达式，也需要同样的检测和入池。

### 当前问题

`try_new_expr()` 的逻辑顺序已经比之前好很多，但它仍然是 GFN pool 的方法：

```
AlphaPoolGFN.try_new_expr(expr, embedding)

```

未来应该变成：

```
FactorCandidateEvaluator.evaluate(candidate, context) -> FactorEvaluationResult
FactorPool.add(result) -> PoolDecision

```

也就是说：

```
表达式质量检查
语法检查
求值
IC/IR/RankIC
新颖性
池内相关性
输出

```

都应从 `AlphaPoolGFN` 抽离。

### 建议拆分

新增：

```
src/factor_core/candidate.py
src/factor_core/pool.py
src/factor_core/pool_policy.py
src/factor_core/candidate_evaluator.py
src/factor_core/output_schema.py

```

其中：

```
@dataclass
class FactorCandidate:
    factor_id: str
    expression: str
    engine: str
    engine_version: str
    created_at: str
    metadata: dict

```

```
@dataclass
class FactorEvaluationResult:
    candidate: FactorCandidate
    syntax: SyntaxCheckResult
    semantic: SemanticCheckResult
    value: ValueCheckResult
    metrics: dict
    novelty: dict
    score: float
    decision: str
    rejection_reason: str | None

```

```
class FactorPool:
    def add(self, result: FactorEvaluationResult) -> PoolDecision:
        ...

```

然后 `AlphaPoolGFN` 只需要负责 GFN reward 的适配：

```
class GFNRewardAdapter:
    def reward_from_result(self, result: FactorEvaluationResult) -> tuple[float, float]:
        ...

```

## 2.4 `evaluation` 方向正确，但仍缺少“标准输出对象”

`src/evaluation` 当前包含 `evaluator.py`、`factor_metrics.py`、`panel_ops.py`、`reporting.py`、`topk.py`。这说明评估层已经开始独立。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress-fourth-425/src/evaluation "Finance_factor_digging/src/evaluation at feature/non-data-progress-fourth-425 · 789453/Finance_factor_digging · GitHub"))

`FactorMetricsEvaluator.evaluate_tensor()` 当前计算 daily IC、daily RankIC、ICIR、RankICIR、coverage、positive IC ratio、nan\_ratio，并返回 dict。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress-fourth-425/src/evaluation/factor_metrics.py "Finance_factor_digging/src/evaluation/factor_metrics.py at feature/non-data-progress-fourth-425 · 789453/Finance_factor_digging · GitHub")) 这比之前粗糙版本好，但仍有三点不足：

1. 返回的是普通 dict，不是强 schema；
2. 没有把 universe、date range、target horizon、direction、valid mask 一起记录；
3. 没有统一输出 `factor_values.parquet` / `daily_metrics.parquet` / `summary.json` 的协议。

Alphalens 的 factor IC API 明确把 factor data 组织成以 date 和 asset 为索引的结构，并计算 factor values 与 N-period forward returns 的 Spearman Rank Correlation。([Alphalens](https://alphalens.ml4trading.io/api-reference.html?utm_source=chatgpt.com "API — Alphalens 0.4.1post1+8.g3348e92 documentation")) 这对你很重要：你的评估输出也应该始终带上 `date`、`asset`、`forward_return_horizon`、`universe`，否则后续对比不同引擎会混乱。

### 建议新增

src/factor_eval/evaluator.py
src/factor_eval/value_store.py
src/factor_eval/report_writer.py

```

`FactorMetrics` 不要只包含指标值，还应包含上下文：

class FactorMetricSummary:

    ic_std: float
    ic_ir: float
    rank_ic_mean: float
    rank_ic_std: float

```

## 2.5 `job_spec.py` 仍是“GFN 训练参数 + 数据参数 + 实验参数”混在一起

`MiningJobSpec.REQUIRED_FIELDS` 当前要求 `job_id`、`name`、`dataset_id`、`family_id`、`segment_name`、`train_start`、`train_end`、`test_start`、`test_end`。`OPTIONAL_FIELDS` 包含 `n_episodes`、`pool_capacity`、`encoder_type`、`entropy_coef`、`ssl_weight`、`nov_weight`、`max_expr_length`、`mask_dropout_prob`、`cuda` 等。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/feature/non-data-progress-fourth-425/src/mining/job_spec.py "raw.githubusercontent.com"))

问题是这些字段混杂了三类东西：

```
实验参数：job_id, seed, output_dir
数据参数：dataset_id, segment_name, train/test date, status_filter
因子搜索参数：family_id, max_expr_length
GFN 专属训练参数：encoder_type, entropy_coef, ssl_weight, nov_weight, mask_dropout_prob

```

如果未来引擎是 PySR，`ssl_weight` 和 `entropy_coef` 没意义；如果引擎是 LLM，`n_episodes` 也不一定合适。PySR 官方 API 支持 operator complexity 等符号回归搜索配置，这类配置应该放在 `engine.params` 下，而不是成为全局 job 字段。([Astro Automata](https://astroautomata.com/PySR/v1.5.9/api.html?utm_source=chatgpt.com "API Reference | PySR - Astro Automata"))

### 目标结构

把 job spec 改成：

```
job:
  job_id: mine_stock_moneyflow_20260425
  name: Mine moneyflow factors
  seed: 42
  output_dir: runs/moneyflow
  tags: [moneyflow, gfn, v2]

data:
  dataset_id: cn.stock.moneyflow.daily.v1
  universe_id: cn_a_active_liquid_v1
  frequency: daily
  splits:
    train: ["20170101", "20211231"]
    valid: ["20220101", "20231231"]
    test:  ["20240101", "20260425"]

target:
  type: forward_return
  price_column: close
  horizon: 5
  direction: predictive

search_space:
  family_id: moneyflow_ts_complex
  max_expr_length: 24
  min_expr_length: 6
  operators: inherit
  constants: inherit
  windows: inherit

engine:
  type: gfn
  params:
    n_episodes: 20000
    batch_size: 64
    encoder_type: gnn
    entropy_coef: 0.02
    ssl_weight: 0.5
    nov_weight: 0.3

evaluation:
  metrics: [ic, rank_ic, ic_ir, rank_ic_ir, rolling_ic, topk, turnover, coverage]
  topk: [20, 50, 100]
  rolling_windows: [20, 60, 120]
  min_coverage: 0.65

output:
  formats: [json, parquet, markdown]
  save_factor_values: true
  save_daily_metrics: true
  save_rejections: true

```

这样 `simple_llm`、`pysr`、`alphasage`、`alphaprobe` 只替换 `engine.type` 和 `engine.params`。

# 7. GFN 相对解绑方案

## 7.1 当前绑定链

当前主链大概是：

```
mine_factors.py
  -> build_data_context
  -> build_alpha_context
      -> AlphaPoolGFN
      -> ExpressionQualityValidator
      -> OllamaExpressionEmbedder
      -> FactorMetricsEvaluator
  -> build_gfn_context
      -> GFNEnvCore
      -> SequenceEncoder
      -> EntropyTBGFlowNet
      -> Sampler
  -> run_training_loop
      -> pool.export_pool

```

`mine_factors.py` 的 import 已经证明 GFN 对主入口是强绑定的。([GitHub](https://raw.githubusercontent.com/789453/Finance_factor_digging/feature/non-data-progress-fourth-425/src/mining/mine_factors.py "raw.githubusercontent.com"))

## 7.2 改造后链路

```
run_mining.py
  -> load MiningExperimentSpec
  -> build FactorMiningContext
  -> engine = EngineRegistry.create(spec.engine.type)
  -> raw_candidates = engine.discover(context)
  -> inspector.inspect(candidate)
  -> pool_policy.add(report)
  -> output_writer.write(...)

```

GFN 变成：

```
factor_engines/gfn/engine.py
  -> GFNEnvCore
  -> GFNRewardAdapter
  -> EntropyTBGFlowNet
  -> yield FactorCandidate(...)

```

注意：GFN engine 不直接写 final\_pool，不直接决定最终输出格式。

## 7.3 GFN reward 如何接标准 evaluator

GFN 训练需要 reward，不可能完全不评估。方案是加一个 adapter：

```
class GFNRewardAdapter:
    def __init__(self, inspector: FactorInspector, reward_config: dict):
        self.inspector = inspector

    def score_expr(self, expr: Expression) -> tuple[float, dict]:
        candidate = FactorCandidate(expression=str(expr), engine="gfn")
        report = self.inspector.inspect(candidate, scopes=["train", "valid_fast"])
        reward = self.reward_from_report(report)
        return reward, report.to_dict()

```

这样 GFN 使用同一套检测接口，而不是独立维护一套 `AlphaPoolGFN.try_new_expr()`。

# 16. 最终结论

你的项目现在已经不适合继续“围绕 GFN 修补”。当前代码已经出现了典型的研究项目膨胀：

```
入口强绑定 GFN
评估逻辑藏在 pool 内
表达式质量模块放在 alpha_gfn 下
job spec 混合实验参数、数据参数、引擎参数
输出格式依赖 AlphaPoolGFN.export_pool
测试、文档、旧代码、debug 脚本混在 src 和 prompts 中

```

正确改造方向是：

```
先做平台接口，再放引擎。
先统一输入输出，再追求挖掘算法。
先标准化表达式检查，再讨论 LLM / PySR / AlphaSAGE / AlphaProbe 谁更强。

```

最终你要的结构应该是：

```
数据输入标准化
标的池标准化
目标收益标准化
表达式检查标准化
指标评估标准化
候选输出标准化
挖掘引擎插件化

```

这样 GFN 不会消失，但它会从“整个项目的中心”变成“一个可插拔挖掘引擎”。这才适合后续同时接入 `simple_llm`、`cogalpha`、`pysr`、`alphasage`、`alphaprobe`，也能让每个因子表达式在输出端拥有清晰、可复现、可比较的语法合规性、适用标的范围、时间范围、IC/IR/RankIC、rolling、TopK 和稳定性检测结果。
