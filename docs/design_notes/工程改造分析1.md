### 五、Atomic Layer：这是当前最需要“从原型升级成框架”的模块

你这次特别提到 Atomic Layer 对不同数据区域适配性太弱，这个判断我完全同意，而且我认为这是当前 branch 的**结构性瓶颈**之一。当前 Atomic Layer 的问题不是“没有”，而是“它已经写成了偏 A 股量价的硬编码 builder”。这类实现对于验证 raw+atomic 两层输入是够用的，但对于你后面真正想做的多数据域工程，反而会成为新的瓶颈。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/data_prep/build_atomic_features.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/data_prep/build_atomic_features.py"))

我的建议不是把 Atomic Layer 砍掉，而是立刻把它拆成两层：

第一层是 **atomic family config**，建议按数据域和频率组拆 YAML，例如：

- `atomic_equity_eod.yaml`
- `atomic_futures_eod.yaml`
- `atomic_index_eod.yaml`
- `atomic_option_eod.yaml`
- `atomic_macro_lowfreq.yaml`
- `atomic_orderbook_intraday.yaml`
- `atomic_chip_daily.yaml`
- `atomic_financial_quarterly.yaml`

第二层是 **builder engine**，只做四件事：

1. 校验 `required_columns`
2. 根据 `formula_kind` 分发到执行器
3. 套用统一 fill / mask / clipping / namespace 规则
4. 生成 registry 与统计摘要

也就是说，`build_atomic_features.py` 不应该继续靠 `_compute_atomic_feature()` 里写一长串数据域分支，而应该变成“配置解释器 + 执行器路由器”。这样你以后加新数据族，改的只是 YAML 和少量执行器，而不是继续污染主 builder 脚本。

### 六、关于 `data/factor_ready_filled/feature_A_filled.parquet`：这是当前非常合适的基准测试入口

你提到这个文件测试时可以且需要调用，这个判断是合理的。当前 `preprocess_features.py` 的输出目录就是 `data/factor_ready_filled`，而 `ParquetFeatureLoaderV2` 也明确会去 sibling 目录下找 `factor_ready_filled/feature_A_filled.parquet` 这样的 filled 文件。因此，如果你要先把新架构跑顺，我会建议把它作为最小 smoke-test 基准，而不是一上来就把 atomic、job、screen、lifecycle 全部串起来。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/preprocess_features.py "Finance_factor_digging/src/preprocess_features.py at feature/non-data-progress · 789453/Finance_factor_digging · GitHub"))

最应该先做的 5 个小测试是：

1. **Meta + Loader 测试**：用 `feature_A_filled.parquet` 跑一遍 `DatasetMeta -> ParquetFeatureLoaderV2`，确认 raw/filled path、date range、cache 写入都正常。
2. **Registry 测试**：用 `FeatureRegistryManagerV2` 生成 raw-only、atomic-only、raw+atomic 三种 feature enum，确认签名和 key 体系稳定。
3. **Atomic 构建测试**：只选 2–3 个最简单 atomic 特征，在小时间窗上跑 `build_atomic_features.py`，先把 builder 本身跑通。
4. **Mining 上下文测试**：只跑 `mine_factors.py` 的 context/build 阶段，不训练，确认 `DatasetMeta / JobSpec / FamilySpec / Loader / Registry` 全部能连起来。
5. **Screen 测试**：给 `screen_factors.py` 一个极小的表达式池，先验证 evaluator 和 date split，不做大规模筛选。

在这五步都稳定之前，不建议开始做速度判断或全量 episode 挖掘。

### 七、关于“挖掘速度需要有了解”：现在只能给你结构性判断，不能给你真实 benchmark

这里我需要说实话：我这次是基于最新 branch 的代码结构和实现关系做分析，没有在你的 conda 环境里实际跑 benchmark，所以我不能假装给你一个可信的真实吞吐数字。现在能给你的，是**结构性速度判断**。

从代码形态看，未来可能真正带来速度收益的点已经出现了两个：

- `ParquetFeatureLoaderV2` 的 data view cache；
- filled 文件直接复用而不是每次临时补值。\
  这两点如果主链切通，确实会明显改善 I/O 和 warm-start 速度。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/alphagen_generic/parquet_feature_loader_v2.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/alphagen_generic/parquet_feature_loader_v2.py"))

但当前代码里也有几个明显的速度阻塞点：

- `train_gfn_v2.py` 的 cache 接线还没闭环，warm cache 收益未必能真正吃到。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/train_gfn_v2.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/train_gfn_v2.py"))
- `screen_factors.py` 还是第一版 evaluator，TopK/Stability 都偏简化，真正大批量时很可能仍会落在 Python 循环和频繁表达式回放上。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/mining/screen_factors.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/mining/screen_factors.py"))
- Atomic builder 如果继续以硬编码、逐公式逻辑膨胀，后续在宽表和多数据域上会很难扩容。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/data_prep/build_atomic_features.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/data_prep/build_atomic_features.py"))

所以我现在给你的速度建议不是“这个项目已经快/慢”，而是：**先把接口闭环修掉，再测吞吐，否则你测到的慢很多时候是工程错配，不是算法本身慢。**

### 八、我对当前阶段的最终判断和优先级建议

如果我站在“顶级量化工程负责人 + 工程 reviewer”的角度看这个 branch，我会给出下面的阶段判断：

- **方向正确，骨架已经铺开。**
- **当前最大问题不是缺模块，而是新旧链路混跑和接口不对齐。**
- **Atomic Layer 已经到该从原型升级成配置化框架的时候了。**
- **筛选系统已经起步，但还没有达到你要的 ICIR / TopK / Stability 主导研究口径。**
- **组合脚本还没有真正降级成纯组合器。**
- **生命周期模块仍未正式落地。**

因此我会把接下来优先级排成这样：

**P0：先修收口 bug**\
包括：

- `DatasetMeta` 的 path-based 构造与调用方对齐；
- `FeatureRegistryManagerV2.create_feature_enum()` 签名统一；
- `MiningJobSpec` 可选字段 property 化；
- `mine_factors.py` / `screen_factors.py` 不再从 `dataset_id.split('.')` 猜 domain；
- `train_gfn_v2.py` 和 `alpha_pool_v2.py` / `cache_manager.py` 的 cache API 对齐。\
  这些修完，测试报错会立刻掉一大截。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/mining/mine_factors.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/mining/mine_factors.py"))

**P1：统一主入口**\
决定到底谁是主训练入口：`train_gfn.py` 还是 `train_gfn_v2.py`。只要这件事不做，团队里任何人都可能跑到不同链路上去，报错会持续呈现“随机性”。([GitHub](https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress/src "https://github.com/789453/Finance_factor_digging/tree/feature/non-data-progress/src"))

**P2：把 Atomic Layer 改成 YAML/config 驱动**\
这是当前最重要的结构升级，不然你后面多域扩展会越来越难。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/data_prep/build_atomic_features.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/data_prep/build_atomic_features.py"))

**P3：让筛选口径真正切到 ICIR / TopK / Stability**\
把 `screen_factors.py` 做成主筛选器，把 `run_adaptive_combination.py` 降级成组合评估器。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/mining/screen_factors.py "https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/mining/screen_factors.py"))

**P4：再做 preprocess 参数化、manifest、统一日志和生命周期模块**\
这些都重要，但在主链路没收口前，优先级次于 P0/P1/P2/P3。([GitHub](https://github.com/789453/Finance_factor_digging/blob/feature/non-data-progress/src/preprocess_features.py "Finance_factor_digging/src/preprocess_features.py at feature/non-data-progress · 789453/Finance_factor_digging · GitHub"))

一句话总结：**这个 branch 已经从“构想”走到“半成品工程”，现在最需要的不是继续横向加功能，而是把已有 v2 模块彻底接成一条闭环主链，然后再做口径升级和生命周期管理。**
